## 1. RAGとは何か（座学・45分）

### 1.1 なぜRAGが必要なのか

Claudeのような大規模言語モデル（LLM）は非常に高性能ですが、次のような弱点があります。

| LLM単体の弱点 | 具体例 |
|---|---|
| 学習データのカットオフ以降の情報を知らない | 「先月改定された社内規定」を知らない |
| 会社固有・非公開の情報を知らない | 「うちの会社のVPNのサーバーアドレス」を知らない |
| 知らないことでも、もっともらしく答えてしまう（ハルシネーション） | 存在しない社内制度をでっち上げて回答してしまう |

これらを解決するアプローチの一つが **RAG（Retrieval-Augmented Generation／検索拡張生成）** です。

> **RAGの基本アイデア**
> LLMに「知識」を全部覚えさせるのではなく、質問のたびに
> 「関連する社内文書を検索して」「その内容を参考情報としてLLMに渡し」「それをもとに回答させる」
> という仕組みにすることで、LLMが知らない・古い情報でも正確に答えられるようにする。

似たアプローチとして「ファインチューニング（LLM自体を再学習させる）」もありますが、
RAGのほうが（1）文書の更新が反映しやすい、（2）学習コストがかからない、
（3）回答の根拠（出典）を示しやすい、という利点があり、社内向けQ&Aボットでは
RAGが第一選択になることが多いです。

### 1.2 RAGの全体像

RAGは大きく2つのパイプラインに分かれます。

```
【Indexing（索引作成）パイプライン】 ※事前に1回、文書が更新されたら再実行

  社内文書              チャンク分割           埋め込み               ベクトルDBに保存
 （FAQ, 規定等） ──▶  （検索しやすい単位に分割） ──▶ （数値ベクトル化） ──▶ （Chroma等）


【Query（質問応答）パイプライン】 ※質問のたびに毎回実行

  ユーザーの質問 ──▶ 質問も埋め込みに変換 ──▶ ベクトルDBで類似検索 ──▶ 関連チャンクを取得
                                                                          │
                                                                          ▼
                                                    質問＋関連チャンクをLLMに渡して回答生成
                                                                          │
                                                                          ▼
                                                                       ユーザーへ回答
```

今日のハンズオンでは、この図の各矢印を1つずつ、自分の手でコードとして実装していきます。

### 1.3 各コンポーネントの役割（用語整理）

| 用語 | 役割 | 今日使うツール |
|---|---|---|
| **チャンク（Chunk）** | 文書を検索しやすい大きさに分割した断片 | 自作の関数（`utils.py`） |
| **埋め込み（Embedding）** | テキストの「意味」を数値のベクトルで表現したもの。意味が近い文章ほどベクトルも近くなる | `sentence-transformers` |
| **ベクトルDB（Vector Store）** | 大量の埋め込みベクトルを保存し、「似ているベクトル」を高速に検索できるデータベース | `Chroma` |
| **検索（Retrieval）** | 質問文の埋め込みに近いチャンクをベクトルDBから取り出す処理 | `Chroma`のクエリ機能 |
| **生成（Generation）** | 検索結果を参考情報としてLLMに渡し、自然な文章で回答させる処理 | `Claude API` |

**ポイント：** 検索（Retrieval）は「意味が近い文章を探す」だけであり、
質問に直接答えるのはあくまでLLM（Generation）の役目です。
この2段階に分かれていることがRAGの理解の鍵になります。

## 3. ハンズオン1: ドキュメントの読み込みとチャンク分割（60分）

**対応ファイル:** `code/step1_load_and_chunk.py`, `code/utils.py`

### 3.1 なぜチャンク分割が必要なのか

長い文書をそのままLLMに渡すのではなく、なぜ小さな断片（チャンク）に分割するのでしょうか。

- **検索の精度向上**：文書全体を1つの塊として検索すると、「一部だけ関連する長い文書」も
  「全体的に関連する短い文書」も同じように扱われてしまい、精度が落ちる
- **LLMへの入力コスト削減**：関連する部分だけをLLMに渡すことで、トークン数（＝コスト）を抑えられる
- **LLMのコンテキスト長には限界がある**：文書全体を毎回渡すのは非効率かつ非現実的

### 3.2 チャンク分割のパラメータ

`utils.py` の `split_into_chunks()` 関数は、2つのパラメータを取ります。

| パラメータ | 意味 | 今回のデフォルト |
|---|---|---|
| `chunk_size` | 1チャンクあたりの目安文字数 | 400文字 |
| `chunk_overlap` | 隣接するチャンク同士で重複させる文字数 | 80文字 |

**オーバーラップがなぜ必要か：** チャンクの境目でちょうど文脈が分断されてしまうと、
「その文だけでは意味がわからない」チャンクができてしまいます。
少し重複を持たせることで、境界をまたぐ情報も拾いやすくなります。

### 3.3 実行してみる

```bash
python step1_load_and_chunk.py
```

出力されたチャンクを眺めながら、以下を確認しましょう。

- 1つのチャンクの中に、意味のまとまりとして自然な内容が入っているか
- 見出し（`#`）や表（Markdownテーブル）がチャンクの途中で分断されていないか

▶ **演習1**（`exercises/exercises.md`）: `chunk_size` と `chunk_overlap` を変えて再実行し、違いを観察してください。

## 4. ハンズオン2: 埋め込みとベクトルDBへの格納（75分）

**対応ファイル:** `code/step2_build_vectorstore.py`

### 4.1 埋め込み（Embedding）とは

埋め込みモデルは、テキストを「数百次元の数値ベクトル」に変換します。
このとき、**意味が近い文章ほど、ベクトル空間上でも近い位置に配置される**という性質があります。

例えば「パスワードを忘れた」と「ログインできない」は文字としては全く違いますが、
埋め込みベクトルにすると近い位置になります。これがキーワード検索（文字列一致）と
ベクトル検索（意味の近さ）の決定的な違いです。

### 4.2 今回使用するモデル

```python
EMBEDDING_MODEL_NAME = "paraphrase-multilingual-MiniLM-L12-v2"
```

- Hugging Face上で無料公開されている多言語対応モデル
- 日本語・英語を含む50以上の言語に対応
- モデルサイズが比較的小さく（約470MB）、ノートPCでも十分な速度で動作する
- **API課金は一切発生しない**（自分のPC上で計算が完結する）

### 4.3 ベクトルDB（Chroma）とは

Chromaは、Pythonから `pip install` するだけで使えるオープンソースのベクトルDBです。
大量のベクトルの中から「質問ベクトルに近いものトップN件」を高速に検索できます。

```python
client = chromadb.PersistentClient(path="./chroma_db")
collection = client.create_collection("it_helpdesk_docs")
collection.add(ids=..., embeddings=..., documents=..., metadatas=...)
```

`PersistentClient` を使うことで、`./chroma_db` フォルダにデータが保存され、
プログラムを再起動しても検索できる状態が維持されます。

### 4.4 実行してみる

```bash
python step2_build_vectorstore.py
```

初回実行時はモデルのダウンロードが発生するため、数分かかる場合があります
（前日の事前準備で完了していれば、当日はすぐに終わります）。

実行後、`code/chroma_db/` フォルダが作成されていることを確認しましょう。
このフォルダの中に、全チャンクのベクトルデータが保存されています。

## 6. ハンズオン4: LLMによる回答生成（90分）

**対応ファイル:** `code/step4_rag_answer.py`

いよいよRAGの最後のピース、LLM（Claude）を使った回答生成です。
このステップで初めてAPI課金が発生します。

### 6.1 プロンプトの組み立て方

検索で得たチャンクを「参考情報」として、質問と一緒にLLMに渡します。

```python
def build_user_prompt(query, retrieved_chunks):
    context = "\n\n".join(f"[出典: {id}]\n{text}" for id, text in retrieved_chunks)
    return f"""# 参考情報
{context}

# 質問
{query}
"""
```

### 6.2 ハルシネーション対策としてのシステムプロンプト

RAGを組んだからといって、自動的にハルシネーションがなくなるわけではありません。
**「参考情報にないことは答えるな」と明示的に指示すること**が非常に重要です。

`step4_rag_answer.py` の `SYSTEM_PROMPT` を見てみましょう。

```python
SYSTEM_PROMPT = """あなたはTechFlow株式会社のITヘルプデスク担当者です。
以下の「参考情報」だけを根拠にして、社員からの質問に日本語で答えてください。

ルール:
- 参考情報に書かれていないことは、絶対に推測や一般知識で補わないこと。
- 参考情報に答えが見当たらない場合は、正直に「社内文書からは確認できませんでした。
  ITヘルプデスク（内線1234）に直接お問い合わせください」と答えること。
- 回答は簡潔に、必要であれば箇条書きを使うこと。
- 参考情報のどの文書に基づいた回答か、末尾に出典として示すこと。
"""
```

このように、モデルの「振る舞い方」を明示的に指示することで、
「わからないことは正直に『わからない』と言う」挙動を引き出しやすくなります
（ただし100%保証されるものではない点にも注意してください）。

### 6.3 使用モデルとコストについて

```python
LLM_MODEL = "claude-haiku-4-5"
```

Claude Haiku 4.5 は、Anthropicのモデルの中で最も高速・低コストなモデルです
（2026年時点で、入力$1／出力$5・100万トークンあたり）。
FAQボットのような「参考情報をもとに簡潔に答える」タスクには十分な性能があり、
コストを抑えたい研修・PoC（概念実証）段階に適しています。

`step4_rag_answer.py` を実行すると、回答と一緒に概算コストが表示されます。

```
--- 今回の概算コスト ---
入力トークン: 612 / 出力トークン: 187
概算コスト: $0.00154（約0.24円）
```

### 6.4 実行してみる

```bash

```

## 8. コスト管理のポイント（振り返り）

本日の研修全体を通じて意識してきたコスト管理の考え方を整理します。

1. **無料でできる部分は無料で済ませる**：埋め込み・ベクトルDB・チャンク分割はすべてローカル実行
2. **課金が発生する箇所を明確に区別する**：LLM呼び出し（Generation）だけが課金対象
3. **安価なモデルから始める**：Haiku級の低コストモデルでまず動くものを作り、精度が足りない場合にのみ上位モデルを検討する
4. **1回あたりのコストを可視化する**：`step4_rag_answer.py` のように、都度コストを表示することで感覚をつかむ
5. **利用上限額を設定する**：Anthropic Consoleで組織/APIキー単位の予算アラートを設定しておく

本番運用でリクエスト数が増える場合は、以下の追加施策も検討してください（発展学習）。

- **プロンプトキャッシュ**：同じシステムプロンプトを繰り返し使う場合、キャッシュにより大幅なコスト削減が可能
- **バッチ処理（Batches API）**：リアルタイム応答が不要な用途では、通常の半額で処理できる

## 9. トラブルシューティング

| 症状 | 原因・対処 |
|---|---|
| `ModuleNotFoundError` が出る | 仮想環境が有効化されているか確認し、`pip install -r requirements.txt` を再実行 |
| `sentence-transformers` のダウンロードが遅い/失敗する | ネットワーク環境を確認。社内プロキシ配下の場合は情報システム部にプロキシ設定を確認 |
| `chromadb.errors.InvalidCollectionException` 等が出る | `step2_build_vectorstore.py` を未実行、または `chroma_db` フォルダが壊れている可能性。フォルダを削除して再実行 |
| `anthropic.AuthenticationError` が出る | `.env` の `ANTHROPIC_API_KEY` が正しく設定されているか確認。`.env.example` からコピーしたか確認 |
| `anthropic.RateLimitError` が出る | 短時間に大量のリクエストを送っている可能性。少し待ってから再実行 |
| 検索結果が期待したものと違う | チャンク分割のされ方を`step1`で確認。文書の書き方（見出しの粒度等）を見直す余地がないか検討 |

## 11. 講師向け進行メモ

- **演習1〜4は受講者の理解度に応じて時間配分を調整可能**です。時間が押している場合は
  演習2（検索の距離観察）を簡略化し、演習3（ハルシネーション観察）は必ず時間を確保してください
  （RAGの本質的な価値・限界を体感できる最重要パートです）。
- コストが心配な受講者向けに、Anthropic Consoleでの**利用上限額の設定方法**を
  冒頭で案内しておくと安心感が増します。
- 質問が広がりやすいポイント：「なぜベクトル検索でキーワード検索じゃダメなのか」
  「ファインチューニングとの違いは」「本番ではどのくらいの規模の文書まで扱えるのか」
  →いずれも本テキスト7.1節の発展トピックに接続して回答するとよいでしょう。
- ハンズオン中に個別のPCでダウンロードが遅い受講者が出た場合に備え、
  事前準備済みの `chroma_db` フォルダのバックアップをUSBメモリ等で講師が用意しておくと安心です。
